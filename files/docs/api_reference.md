# FloodWatch API Reference

This is a compact reference for the active FastAPI endpoints used by the approved core system.

## Operational extension (2026-09-08)

The table below supplements the earlier core reference. Public reads remain available. Role-gated API calls accept a valid bearer token or session cookie; 401 means no valid session and 403 means insufficient role. Public registration always creates an ordinary user. Initial privileges are assigned with `manage_operator.py` from the server terminal.

| Route | Access | Result |
|---|---|---|
| `GET /health` | Public | 200 with database healthy; 503 if unavailable; separate model status |
| `GET /evaluation` | Public | Model charts with textual values |
| `GET /api/model-evaluation` | Public | Saved synthetic metrics, confusion counts and generation/retrieval times |
| `GET /api/model-evaluation/report.pdf` | Public | Complete saved evaluation report |
| `GET /api/news-feed?limit=8&refresh=false` | Public | Configured NewsAPI/GNews/RSS articles or setup/failure state |
| `POST /api/telemetry/upload-csv` | Operator/admin | Multipart field `file`; 2 MB/2,000 rows maximum; accepted/rejected counts |
| `GET /api/alerts` | Public; private notes restricted | Persistent risk events with workflow status |
| `POST /api/alerts/dispatch` | Operator/admin | `station_id`; simulated log only |
| `POST /api/alerts/{id}/acknowledge` | Operator/admin | JSON `notes` (up to 1,000 characters), status and audit update |
| `POST /api/alerts/{id}/escalate` | Operator/admin | Internal review escalation; no delivery claim |
| `POST /api/alerts/{id}/resolve` | Operator/admin | Close review event; later elevated readings can create a new event |
| `GET /api/alerts/{id}/audit` | Operator/admin | Action, previous/new status, notes, operator and time |
| `POST /api/scenario/run` | Operator/admin | `station_id`, `scenario` = `normal` or `flood`; simulated reading and saved run |
| `GET /api/scenario-runs` | Operator/admin | Stored runs with holdout-evaluation snapshots |
| `GET /api/scenario-runs/{id}/report.pdf` | Operator/admin | Scenario before/after evidence and saved model snapshot |
| `GET /api/auth/me` | Account | Current profile and role |
| `GET /api/admin/users` | Admin | Accounts/roles; no passwords or session tokens |
| `PATCH /api/admin/users/{id}/role` | Admin | JSON `role` = `viewer`, `operator`, `admin`; last-admin demotion rejected |
| `POST /logout` | Browser session | Revoke current session and redirect Home; GET is not a logout action |

Illegal or repeated workflow transitions return 409. Missing event/run IDs return 404. CSV field validation errors are listed per rejected row; structural parse errors return 422 before imports begin. Numeric telemetry must be finite. Pagination rejects negative `skip` and limits outside 1–1,000. Optional `FLOOD_EWS_INGEST_TOKEN` requires `X-Ingest-Token` for sensor POSTs; no key is required by the local-demo default.

See [operational_platform_guide.md](operational_platform_guide.md) and [provider_setup.md](provider_setup.md). A scenario PDF does not claim a new accuracy measurement from a single injected reading. Real messaging and hosted deployment remain unverified.

Base URL during local development:

```text
http://127.0.0.1:8000
```

## 1. Store telemetry

```text
POST /api/telemetry
```

Purpose: receive one simulated or hardware sensor reading and save it in the database.

Example request:

```json
{
  "station_id": "STN-01",
  "station_name": "Lokoja (Niger-Benue confluence)",
  "data_source": "simulated",
  "lat": 7.7999,
  "lon": 6.7333,
  "timestamp": "2026-09-03T12:00:00Z",
  "water_level_m": 4.5,
  "danger_level_m": 5.5,
  "rainfall_mm_hr": 12.0,
  "flow_rate_m3s": 45.0,
  "battery_pct": 98.5,
  "signal": "online"
}
```

Successful response: HTTP `200`, with the saved telemetry row and generated database `id`.

## 2. Read telemetry

```text
GET /api/telemetry
```

Purpose: return stored telemetry rows for the flood data page and manual inspection.

Rows are returned newest-first so the most recent simulator or hardware reading is easiest to inspect.

Optional query:

```text
GET /api/telemetry?data_source=hardware
```

Supported `data_source` values:

- `simulated`
- `hardware`

Unsupported source names return HTTP `422`.

## 3. Read newest risk status

```text
GET /api/risk-status
```

Purpose: return the newest risk-status row per station for the dashboard map and accessible station list.

Optional source modes:

```text
GET /api/risk-status?data_source=simulated
GET /api/risk-status?data_source=hardware
GET /api/risk-status?data_source=hybrid
```

Mode meanings:

- `simulated` shows only readings generated by the simulator.
- `hardware` shows only readings posted by a physical or hardware-style sensor node.
- `hybrid` compares the newest simulated and hardware readings per station/source pair and displays the currently more serious risk. This is useful during demonstrations where a simulator is running while a hardware node is also being tested.

The response includes:

- station identity and coordinates;
- source provenance;
- latest water level and danger level;
- rainfall, flow, battery, and signal state;
- measured `rate_of_rise_m`, calculated from the same station and same telemetry source;
- risk level;
- risk ratio;
- ML probability if the model is available;
- safe advisory message;
- alert-channel simulation status.

Implementation note: `/api/risk-status` uses database-side latest-record queries. Source-specific mode fetches the newest row per station; hybrid mode fetches the newest row per station/source pair and displays the more serious current risk.

## 4. Dashboard and data pages

```text
GET /dashboard
GET /data
```

Purpose:

- `/dashboard` serves the GIS decision-support dashboard.
- `/data` serves the telemetry table view.

These pages are available for the approved core demonstration without requiring account login.

## 5. Favicon

```text
GET /favicon.ico
```

Purpose: serve the FloodWatch SVG icon so browser requests do not create distracting `404` lines during demonstrations.

## 6. Optional account shell

The project contains optional account routes, but advanced account-dependent product features are parked until supervisor approval. The approved core system does not depend on account login.

The optional account shell currently supports:

- `POST /api/auth/register`, requiring first name, last name, email, phone number, and password;
- `POST /api/auth/login`, returning a bearer token for API-style testing;
- browser registration preview before account creation, so a user can confirm typed details before the account is saved;
- browser login that returns users to the home page by default;
- settings/profile update for names, phone number, and simulated notification preferences;
- two-step account deletion using a locally logged verification code, feedback reason, and final `DELETE` confirmation.

Account-deletion and contact notices are simulated and written to `files/api/simulated_account_notifications.jsonl`. No real SMS, email, or WhatsApp message is sent unless a real provider is configured and tested. WhatsApp is saved only as a future contact preference; it is not an active alert channel in the approved core system.

## 7. Error examples

The API returns HTTP `422` for invalid telemetry, such as:

- unknown `data_source`;
- latitude outside `-90` to `90`;
- zero or negative `danger_level_m`;
- battery percentage above `100`;
- missing required station fields.

These rejection cases are tested in `files/api/test_api.py`.
